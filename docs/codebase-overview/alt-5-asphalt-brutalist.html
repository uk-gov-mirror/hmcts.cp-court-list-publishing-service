01

What this is (and is not)

This repo is an HMCTS Modern by Default service cut from service-hmcts-crime-springboot-template. It is NOT a CQRS, event-sourced cpp-context-* WildFly context. No Maven. No RAML. No event store. One deployable. One status table. Contract-first REST.

The job: an authorised clerk — permission Publish Magistrate Court List — triggers a publish. The service pulls the court-list payload from the Progression query API, transforms it to the CaTH (Court and Tribunal Hearings) document format, scrubs every string (HTML stripping + WAF patterns), validates against a JSON Schema, posts to CaTH through Azure APIM, renders a PDF via the Document Generator, and drops it in Azure Blob Storage. Status lives in court_list_publish_status.

The REST contract is generated from api-cp-crime-court-list-publisher:0.1.22. You do not write routes by hand here. Ever.

03

One request, nine hits

  1. POST /courtlistpublishing-service/courtlistpublish hits CourtListPublishController (implements generated CourtListPublishApi). Filters first: JWTFilter, then auth-rules demanding Publish Magistrate Court List. No CJSCPPUID header → 400. End of story.
  2. CourtListPublishStatusService.createOrUpdate upserts the status row — court centre, list type, date range — and returns courtListId.
  3. CourtListTaskTriggerService enqueues PUBLISH_AND_PDF_GENERATION_TASK via task-manager-service. HTTP returns immediately. Everything real happens async.
  4. Task wakes, unpacks jobData, calls CourtListQueryService → Progression query API for the raw payload.
  5. Transformation strategy by CourtListType: Standard or OnlinePublic, enriched with courtrooms + LJA from ReferenceDataService.
  6. CourtListDocumentSanitizer strips HTML and WAF-trigger patterns (mandatory fields protected by RequiredStringFieldsRegistry); then JsonSchemaValidatorService judges it against the standard / online-public schema.
  7. CaTHService / CaTHPublisher POSTs to CaTH via APIM. Feature-flagged: cath.publishing-enabled. Off → StubCourtListPublisher.
  8. CourtListPdfHelper → DocumentGeneratorClient renders the PDF. AzureBlobService uploads it (Azurite locally).
  9. Status flips to PUBLISH_SUCCESSFUL. FileController streams CourtList.pdf on demand.

05

Traps. Read before touching.

  • README = mostly the template's README. It references a docs/ dir that wasn't there. Trust build.gradle, not prose.
  • NO runIntegrationTests.sh. Workspace CQRS rituals do not apply. ITs = gradle integration. And gradle build runs them too — build → check → integration.
  • Docker daemon up FIRST. checkDockerDaemon fails fast. Ports: app 8082, debug 8787→5005, WireMock 8089, Postgres 55432, Azurite 10000.
  • composeDown is commented out on purpose. The stack STAYS UP after ITs. Next composeUp recreates it.
  • The committed Azurite key is Microsoft's public dev key (# gitleaks:allow). Not a leak. Do not "fix".
  • Compile = -Werror. PMD gates PRs. CodeQL + secrets scanner run too.
  • Drift: CI pre-pulls azurite:3.33.0, compose runs 3.34.0. Harmless — pre-pull is cache-warming.
  • Flags: CP_CLP_AUTHZ_ENABLED / CP_CLP_AUDIT_ENABLED / CATH_PUBLISHING_ENABLED. ITs: authz+audit OFF, CaTH ON → WireMock.

The reusable pipeline

  1. ARTEFACT-VERSION. hmcts/artefact-version-action mints draft/release version → -DARTEFACT_VERSION.
  2. BUILD. Temurin 21 + gradle/actions/setup-gradle (cache) + image pre-pull + gradle build. Because build → check → integration, THE FULL IT SUITE RUNS HERE, on the runner. bootJar uploaded as app-jar.
  3. PROVIDER-DEPLOY. gradle publish → GitHub Packages + ADO hmcts-lib feed. Secrets: AZURE_DEVOPS_ARTIFACT_USERNAME/TOKEN.
  4. DEPLOY. hmcts/trigger-ado-pipeline → ADO pipeline 460. Secret: HMCTS_ADO_PAT.

How the ITs run on a runner

ubuntu-latest ships Docker + Compose v2. The Avast Gradle plugin drives the same compose file you run locally — laptop and runner are identical by construction:

gradle integration
  ├─ bootJar                      # compose COPYs the jar into the app image
  ├─ composeUp                    # docker compose up --wait --wait-timeout 120
  │    ├─ app      :8082          # profile=integration, authz/audit OFF
  │    ├─ db       :55432         # postgres:16-alpine, healthcheck-gated
  │    ├─ wiremock :8089          # progression / refdata / CaTH / docgen stubs
  │    └─ azurite  :10000         # blob emulator
  └─ Test task                    # REST-assured vs localhost:8082
# captureContainersOutput=true → app logs land in the Actions job log

Dedicated IT workflow — drop-in

name: Integration Tests
on:
  pull_request: { branches: [ main ] }
  workflow_dispatch:

jobs:
  integration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-java@v5
        with: { distribution: temurin, java-version: '21' }
      - uses: gradle/actions/setup-gradle@v5
        with: { gradle-version: current }
      - name: Warm image cache             # optional anti-flake
        run: |
          docker pull postgres:16-alpine
          docker pull wiremock/wiremock:3.9.1
          docker pull mcr.microsoft.com/azure-storage/azurite:3.34.0
      - name: Run integration tests
        run: gradle integration
      - name: Tear down stack
        if: always()                       # Gradle leaves it up on purpose
        run: docker compose -f docker/docker-compose.integration.yml down -v
      - name: Upload IT report
        if: always()
        uses: actions/upload-artifact@v5
        with: { name: integration-test-report, path: build/reports/tests/integration }

Red build? Do this.

  • Container logs are ALREADY in the job log (capture is on). Read the app stack trace first.
  • composeUp failed → did the 120 s --wait expire before /actuator/health went green?
  • Pull the integration-test-report artifact for the HTML report.
  • Reproduce locally with the same command. Same compose file. No excuses.
