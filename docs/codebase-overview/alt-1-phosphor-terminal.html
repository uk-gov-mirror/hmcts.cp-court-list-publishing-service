CP-COURT-LIST-PUBLISHING-SERVICE(7)

Publishes magistrates' court lists to CaTH (Court and Tribunal Hearings) and generates the printable PDF — fetch, transform, sanitize, validate, publish, store.

Java 21 Spring Boot 4.0.0 Gradle PostgreSQL 16 + Flyway Azure Blob / Azurite Modern-by-Default (not CQRS)
SECTIONS: 1.SYNOPSIS · 2.TREE · 3.LIFECYCLE · 4.ABSTRACTIONS · 5.GOTCHAS · 6.WHERE-TO-START · 7.GITHUB-ACTIONS & INTEGRATION-TESTS

Synopsis

This is an HMCTS "Modern by Default" Spring Boot service, scaffolded from service-hmcts-crime-springboot-template. It is not one of the CQRS/event-sourced cpp-context-* WildFly services: no Maven, no RAML, no event store. One deployable, one Postgres status table, contract-first REST.

The job it does: when a court clerk (holding the Publish Magistrate Court List permission) triggers a publish, the service pulls the court-list payload from the Progression query API, transforms it into the CaTH publication document format, scrubs it (HTML stripping + WAF pattern sanitization), validates it against a JSON Schema, posts it to CaTH through Azure APIM, renders a PDF via the Document Generator, and parks the PDF in Azure Blob Storage for download. Publish status is tracked in the court_list_publish_status table.

The REST contract is generated from an OpenAPI spec artifact — uk.gov.hmcts.cp:api-cp-crime-court-list-publisher:0.1.22 — so controllers implement generated interfaces rather than declaring their own routes.

Lifecycle

Trace of one publish request, entry to output:

  1. POST /courtlistpublishing-service/courtlistpublish lands on CourtListPublishController (implements generated CourtListPublishApi). The filter chain runs first: JWTFilter, then cp-auth-rules-filter enforcing the Publish Magistrate Court List permission. A CJSCPPUID header is mandatory — missing means 400.
  2. CourtListPublishStatusService.createOrUpdate upserts a row in court_list_publish_status (Flyway-managed) keyed by court centre / list type / date range, returning a courtListId.
  3. CourtListTaskTriggerService enqueues PUBLISH_AND_PDF_GENERATION_TASK via the shared task-manager-service library. The HTTP response returns immediately — everything else is asynchronous.
  4. The task (CourtListPublishAndPDFGenerationTask, annotated @Task) wakes up, reads jobData (courtListId, list type, court centre, publish date, userId) and calls CourtListQueryService → Progression query API for the raw payload.
  5. Transformation: StandardCourtListTransformationService or OnlinePublicCourtListTransformationService (strategy by CourtListType), enriching rooms and LJA details through ReferenceDataService.
  6. CourtListDocumentSanitizer scrubs every string (HTML stripping, WAF-trigger patterns; RequiredStringFieldsRegistry guards mandatory fields), then JsonSchemaValidatorService validates the document against schema/standard-court-list-schema.json or schema/online-public-court-list-schema.json.
  7. CaTHService / CaTHPublisher POSTs the document to CaTH via APIM — gated by cath.publishing-enabled (a StubCourtListPublisher stands in when disabled).
  8. CourtListPdfHelper → DocumentGeneratorClient renders the PDF; AzureBlobService uploads it to the blob container (Azurite locally).
  9. Status flips to PUBLISH_SUCCESSFUL / failure state; FileController + CourtListDownloadService stream the PDF back as CourtList.pdf.

Abstractions

  • Generated API interfaces — CourtListPublishApi et al. come from the versioned OpenAPI artifact. To change the contract, bump apiSpecVersion in gradle.properties; never hand-edit routes.
  • ExecutableTask / @Task — the task-manager-service abstraction for durable async jobs. The string ID PUBLISH_AND_PDF_GENERATION_TASK binds trigger to executor.
  • Transformation strategies — BaseCourtListTransformationService with Standard and OnlinePublic variants; output is the CaTH-shaped CourtListDocument tree in models/transformed.
  • Sanitizer chain — HtmlStrippingSanitizer + WafPatternSanitizer behind CourtListDocumentSanitizer; defence against hostile free-text leaking into public documents.
  • Schema validation gate — JsonSchemaValidatorService (everit) is the last quality gate before anything leaves for CaTH.
  • CourtListStatusEntity — the single JPA entity; one table tracks the whole publish lifecycle.
  • Profile-sliced config — application-azure/authz/audit/datasource/jwt.yml; the integration profile rewires everything at WireMock + Azurite.

Gotchas

  • The README is largely the template's README — it links a docs/ directory that does not exist in this repo. Trust build.gradle over the README.
  • No runIntegrationTests.sh here. The workspace-wide CQRS conventions don't apply. ITs run via gradle integration; and note gradle build runs unit and integration tests (build dependsOn integration).
  • Docker must be up before gradle integration — a checkDockerDaemon gate fails fast. Ports: app 8082 (remote debug 8787→5005), WireMock 8089, Postgres 55432, Azurite 10000.
  • composeDown is intentionally commented out — the stack stays up after ITs for debugging; next composeUp recreates it.
  • The committed Azurite account key is Microsoft's public dev key (# gitleaks:allow) — not a leak; override only for real storage accounts.
  • Compiler runs with -Werror; PMD (ruleset in .github/pmd-ruleset.xml) gates PRs via the code-analysis workflow.
  • CI pre-pulls azurite:3.33.0 but compose uses 3.34.0 — harmless drift; the pre-pull is only a cache-warmer.
  • Auth, audit, and CaTH publishing are all feature-flagged (CP_CLP_AUTHZ_ENABLED, CP_CLP_AUDIT_ENABLED, CATH_PUBLISHING_ENABLED) — ITs disable authz/audit and enable CaTH against WireMock.

The reusable pipeline, job by job

  1. Artefact-Version — hmcts/artefact-version-action mints a draft or release version (drives -DARTEFACT_VERSION).
  2. Build — Temurin JDK 21 + gradle/actions/setup-gradle, pre-pulls the compose images, then runs gradle build — which, because build → check → integration, runs the full integration suite inside CI. The bootJar is uploaded as the app-jar artifact.
  3. Provider-Deploy — gradle publish to GitHub Packages and the Azure DevOps hmcts-lib feed (needs AZURE_DEVOPS_ARTIFACT_USERNAME/TOKEN secrets).
  4. Deploy — hmcts/trigger-ado-pipeline kicks ADO pipeline 460 with the artefact coordinates (needs HMCTS_ADO_PAT).

How integration tests actually run on a runner

There is no Testcontainers magic at IT level — the Avast docker-compose Gradle plugin drives docker/docker-compose.integration.yml directly. ubuntu-latest runners ship with Docker, so gradle integration just works:

# what `gradle integration` does on the runner:
bootJar                          # build the app jar (compose COPYs it into the image)
composeBuild + composeUp         # docker compose up --wait --wait-timeout 120
   ├── app       :8082          # Spring profile: integration, authz/audit OFF
   ├── db        :55432         # postgres:16-alpine, healthcheck-gated
   ├── wiremock  :8089          # plays progression / refdata / CaTH / docgen stubs
   └── azurite   :10000         # local Azure Blob
integration (Test task)          # REST-assured against http://localhost:8082/...
# composeDown deliberately NOT finalized — stack stays up for debugging

WireMock mappings under src/integrationTest/resources/wiremock/ are volume-mounted in, so the app's outbound calls (Progression, reference data, CaTH, document generator) are all stubbed on the runner. captureContainersOutput = true streams container logs into the Gradle output — when an IT fails in Actions, the app's own log is right there in the job log.

Running ITs as a dedicated workflow

Today ITs piggyback on gradle build. If you want them as their own job (separate status check, retries without rebuilding), this is the complete workflow:

name: Integration Tests
on:
  pull_request:
    branches: [ main ]
  workflow_dispatch:        # manual re-runs from the Actions tab

jobs:
  integration:
    runs-on: ubuntu-latest  # Docker + compose v2 preinstalled
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-java@v5
        with: { distribution: temurin, java-version: '21' }
      - uses: gradle/actions/setup-gradle@v5
        with: { gradle-version: current }

      - name: Warm Docker image cache   # optional; avoids pull flakiness
        run: |
          docker pull postgres:16-alpine
          docker pull wiremock/wiremock:3.9.1
          docker pull mcr.microsoft.com/azure-storage/azurite:3.34.0

      - name: Run integration tests
        run: gradle integration         # composeUp + ITs, nothing else

      - name: Tear down stack
        if: always()                    # composeDown is not finalized in Gradle
        run: docker compose -f docker/docker-compose.integration.yml down -v

      - name: Upload IT report
        if: always()
        uses: actions/upload-artifact@v5
        with:
          name: integration-test-report
          path: build/reports/tests/integration

Debug checklist for a red IT job: (1) read the inlined container logs in the Gradle output; (2) check the --wait-timeout 120 didn't expire — the app healthcheck polls /courtlistpublishing-service/actuator/health; (3) download the IT report artifact; (4) reproduce locally with the exact same command — the compose file is identical on laptop and runner.
